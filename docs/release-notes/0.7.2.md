## Before you upload

1. **`assetlinks.json` must be published** at
   `https://paramanuseniorshealth.org/.well-known/assetlinks.json`, carrying the SHA-256 of the
   **Play app-signing key** (Play Console → Setup → App integrity — the app-signing key, not the
   upload key, because Play re-signs). Until it is live, `autoVerify` fails, Android 12+ keeps
   sending the link to the browser, and the prefill never runs. Shipping without it is harmless,
   just inert.

2. **The sender's `TestSends.gs` must already be deployed** with
   `TEST_SEND_ATTACHMENT_TOPIC = 'test-notices-v1'` and
   `TEST_SEND_PLAIN_TOPIC = 'test-notifications-v1'`. The app now subscribes to exactly those two
   names; if the deployed sender still sends to `testing-v1`, delivery checks stop arriving
   entirely.

3. **Testers with Testing switched on must open the app once** after updating. `syncSubscriptions`
   unsubscribes `testing-v1` and subscribes the two new topics on the next launch — it does not
   happen while the app is closed.

## Technical, for the record

### The Testing switch is two topics

`TESTING_TOPIC = "testing-v1"` is replaced by `TESTING_ATTACHMENT_TOPIC = "test-notices-v1"` and
`TESTING_PLAIN_TOPIC = "test-notifications-v1"`, held together as `TESTING_TOPICS`.

The sender splits its test sends by shape: anything carrying a PDF or an image goes to the
attachment topic, everything else to the plain one. A phone with the switch on needs both, or half
the delivery checks never arrive.

Migration is automatic and needs no code of its own: `testing-v1` is in the stored subscription set
and no longer in the desired one, so `syncSubscriptions` unsubscribes it on the next launch. The
failed-unsubscribe retry already in that method covers a phone that is offline at the time.

### The activation link fills the code in

The `/activation` intent filter was declared in 0.7.1's manifest but nothing ever read
`intent.data`, so a verified link opened the app and silently dropped the code — leaving the reader
at an empty field, worse off than if the link had opened the website.

`ActivationLink` now parses it. Deliberately free of Android imports, like `FetchPolicy`, so the
whole judgement about what counts as an activation link is unit-tested on the JVM (11 tests).

Three decisions worth keeping:

- **Host and path are checked in code, not only in the manifest.** `MainActivity` is exported, so
  any installed app can hand it an `ACTION_VIEW` intent carrying a URI the intent filter never
  vetted. There is a test for the `notparamanuseniorshealth.org` lookalike.
- **A link only ever prefills; it never submits.** Redeeming spends the code against this phone and
  cannot be undone from the app, so that stays behind the button the user presses. A link forwarded
  on to someone else must not be able to claim a code merely by being opened.
- **The code goes through the same `clean()` as typing and pasting.** A link cannot put anything in
  the field that a user could not have typed, and a stale or malformed code fails visibly in the
  field rather than vanishing on the way in.

A link arriving on a phone that already holds a working code raises a toast and goes no further.
Revoked phones are excluded from that test — such a phone still holds a code but is not activated,
and is exactly the phone a replacement link is meant for, so its link reaches the field.
