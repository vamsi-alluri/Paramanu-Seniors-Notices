# 0.8.4 — versionCode 20

Prepared 2026-10-28. Changes since 0.8.1 (versionCode 17), the build in production. Three pieces:
control messages move off the shared broadcast onto a topic per phone and per dispensary, the
activation link is fixed for a revoked phone and for a link copied out of a browser, and a phone
whose code was unlinked can take it back. No database or rules change.

**This build leaves `control-v1`.** Unless the two new database triggers are deployed before it
reaches phones, it gets no pushed revoke, resume or banner at all, and finds them only at its next
check. See "Before you upload".

---

## Play Console — "What's new"

Copy everything inside the block.

```
- Activation links copied from the website now open the app every time.
- If your code has been stopped, the link for a new code takes you straight to where you type it, and shows your old code so you know which one not to use.
- Fixed a message that wrongly said the phone was already activated, just after activating it from a link.
```

The move to per-phone topics is invisible to a reader, and so is taking back an unlinked code: it
only ever happens at the helpdesk's suggestion.

## Before you upload

1. **Stop the old Apps Script drain first.** In the sender, run `controlStopTrigger()` (or delete
   the `controlRun` trigger under Triggers), then delete `Control.gs`. Do this **before** step 2:
   with both running, a phone on 0.8.1 or older gets each disable twice, with two different stamps,
   applies both, and posts the "removed" notification twice.

2. **Deploy the triggers.** Merging `functions/` to `main` runs the workflow, which now deploys
   `codeManagement`, `codeControl` and `bannerControl`. The first deploy also grants the runtime
   account its Eventarc roles; the deployer can do that (runbook section 8). Then prove it: disable
   and enable a test code, save a banner, and look for `control revoke sent`, `control legacy-revoke
   sent`, `control resume sent` and `control banner sent` in the logs (commands in section 8).

3. **Paste the Apps Script copies**: sender `Code.gs` and `Tests.gs`, console `Code.gs`,
   `Tests.gs` and `Index.html`. Then delete `/controlQueue` in the database. The console still works
   if this lags: it would only keep writing queue entries that nothing reads.

4. **`code_management_base_url` stays published** in Remote Config, as for 0.8.1.

5. **Leave the database rules alone.** Builds up to 0.8.0 still read `/codes` and `/dispensaries`
   directly. Closing the rules is the breaking step, and waits until those builds have aged out
   (plan phase 5).

Steps 1 to 3 do not depend on this build and can go out today; they also restore pushes to the
builds already in the field, through the bridge below.

## Technical, for the record

### Control messages: one topic per phone, one per dispensary

`control-v1` carried every revoke, resume and banner to every phone, and each phone compared the
code with its own. Now:

| Topic | Carries | Held by |
|---|---|---|
| `device-v1-<uid>` | revoke, resume | the install holding a claim, revoked or not |
| `banner-v1-<dispensaryId>` | banner | phones whose code names that dispensary, while not revoked |

`ControlTopics` builds both names. The UID is used exactly as Firebase issued it, since topics are
case-sensitive and the function builds the name from the same `usedBy`. A name outside FCM's
grammar is not subscribed rather than retried every launch.

`syncSubscriptions` subscribes the device topic whenever the phone holds a claim and the banner
topic only while it stands. `control-v1` is left by the existing mechanism, with no new code: it is
in every install's stored subscription set (topic tracking and `control-v1` arrived together, in
0.5.0) and no longer in the desired one, so the next sync unsubscribes it.

The messages are sent by two Realtime Database triggers in `functions/src/control.ts`, replacing
the console's `/controlQueue` and the sender's one-minute `Control.gs` drain:

- **`codeControl`** compares `/codes/{code}` before and after each write, and addresses only the
  phone that held it before. Its claim stopping (disable, unlink, delete, `usedBy` changed) is a
  revoke; its claim coming back is a resume; a fresh claim sends nothing. It re-reads the node and
  drops a message the database no longer supports. The stamp is the write's own time.
- **`bannerControl`** pushes when `html` or `htmlUpdated` changes, with the banner as it is now, not
  the write's after-image, stamped with `htmlUpdated`.
- Neither logs the UID or the code.

**Unlink is now pushed.** The old drain could not push it: a revoke broadcast by code could cut off
whoever claimed the code next. A reinstall has a new UID, so the next holder cannot receive the old
phone's device topic, and unlinking now reaches the old phone in seconds.

**The `control-v1` bridge** (temporary). Until the rules close, both triggers also send a copy to
`control-v1`, in the old envelope, so 0.8.1 and older keep getting pushes. Only what the old drain
sent: banners, and a disable or enable of a code a phone still holds. Never an unlink or a delete,
for the reason above. A phone on this build that has not yet left `control-v1` receives a message
both ways with the same stamp and applies it once. Removed with the rules (runbook section 8).

### A second revoke is ignored

Unlinking a code that was already disabled sends a second revoke, for the phone that missed the
first. A phone that is already revoked now records the stamp and does nothing else; without this
it would post the "removed" notification again for a change the user cannot see.

### Disable pauses a code, Unlink recycles it

A revoked phone that types or scans its own code now asks the server instead of being answered
"same code" on the phone (`RedeemPolicy.localAnswer`). If the code was unlinked it is free, and
this phone claims it again like any other phone would. If it is still disabled, or another phone
has claimed it since, the refusal is shown as the existing same-code message (`resultFor`, with
`ownCode`).

The on-phone block gave no security: it fell to a reinstall, the code is printed on the revoked
banner, and the notices are public. Disable is what keeps someone out, on the server and for every
phone. A lost or stolen phone is Disabled and its holder given a new slip; the console's Unlink
confirmation now says so. Reasoning in `docs/decisions.md`, "Disable pauses a code, Unlink recycles
it".

### Activation links

- **`/activation/` is matched as well as `/activation`.** The site serves the page at the slashed
  path and redirects the bare one there, so a link copied out of a browser carried the slash and
  opened in the browser instead of the app.
- **On a revoked phone a link opens the code screen.** Before, it filled a field the user could
  only reach through Settings, so a replacement slip scanned from the notice list looked like a scan
  that did nothing. Its own stopped code included, now that an unlinked code can be taken back.
- **The code screen shows the stopped code** when the phone is revoked, however it was reached:
  "This phone's old code", the code struck through, "This code has been stopped." Below the button,
  so the one code on screen that does not work is never the first one read; struck through so the
  meaning does not rest on colour.
- **No more false "already activated".** The link effect was keyed on both the link and
  "already activated", so redeeming the code a link had filled flipped the second key with the link
  still held, and the user who had just activated was told the phone was already activated. It is
  now judged once, when the link arrives, and a link whose code has been redeemed is dropped.

### Verification

Unit tests pass (`:app:testDebugUnitTest`), including new ones for the topic names and the
own-code redeem cases. Functions: 107 tests under the emulator. **Not yet walked on a device.**
Worth walking before release, on a Play-signed install (a debug build fails link verification):

- A fresh activation subscribes `device-v1-<uid>` and `banner-v1-<id>`, and an upgrade from 0.8.1
  leaves `control-v1`: `subscribed_topics` in
  `adb shell run-as org.paramanuseniorshealth.notices cat shared_prefs/activation.xml` (debug
  builds only), and no `Subscribe to '...' failed` lines under the `ActivationRepo` log tag.
- Disable the code in the console: the banner appears within seconds. Enable: it clears.
- Save a banner: the header changes within seconds.
- Unlink the code: the phone is revoked within seconds; retyping the same code takes it back.
- Disable, then retype the same code: the same-code message.
- Scan a slip's QR on a revoked phone: the code screen opens with the old code shown.
